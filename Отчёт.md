# Uptime Monitor

## 1. Доменная область

Uptime Monitor предназначен для контроля доступности HTTP/HTTPS-сервисов.
Пользователь создаёт monitor, указывает название сервиса, URL, периодичность проверки, timeout и признак активности.
Приложение автоматически обращается к URL, сохраняет результат в PostgreSQL и показывает текущее состояние и историю проверок.

Проверка считается успешной, если сервис вернул HTTP status от 200 до 399 включительно.
Ответы 4xx и 5xx, timeout, DNS-ошибки и ошибки соединения считаются неуспешными.

## 2. Стек реализации

- Go 1.26
- `net/http` и `chi` для HTTP/REST API
- `pgx/v5/pgxpool` для работы с PostgreSQL
- `log/slog` для структурированных логов
- HTML, CSS и Vanilla JavaScript для frontend
- Docker и Docker Compose
- SQL migrations через отдельный migration service

## 3. Основные сущности

### Monitor

Monitor описывает сервис, который нужно проверять:

- `id`
- `name`
- `url`
- `interval_seconds`
- `timeout_seconds`
- `enabled`

### Check

Check описывает результат одной проверки:

- `id`
- `monitor_id`
- `status` — `up` или `down`
- `status_code`
- `latency_ms`
- `error`
- `checked_at`

Статус `unknown` не является сущностью базы данных. Он вычисляется на уровне API и frontend, если у monitor ещё нет checks.

## 4. Соответствие методологии 12 факторов

### 1. Кодовая база

Весь проект находится в одном репозитории Git и представляет собой одну кодовую базу.

### 2. Зависимости

Все Go-зависимости объявлены в `go.mod` и зафиксированы в `go.sum`.
ORM и неявные системные зависимости для работы приложения не используются.

### 3. Конфигурация

Значения, зависящие от окружения, вынесены в переменные окружения: порт HTTP-сервера, строка подключения PostgreSQL, параметры пула рабочих и планировщика.
Пример конфигурации находится в `.env.example`.
Локальные значения для разработки находятся в `.env`. Время ожидания подключения к PostgreSQL и корректного завершения задаются через переменные окружения, а время ожидания проверки готовности Docker зафиксировано в Compose.

### 4. Внешние службы

PostgreSQL подключается как внешняя служба через `DATABASE_URL`.
Приложение не зависит от локального файла базы данных.

### 5. Сборка, выпуск и запуск

Dockerfile отдельно собирает бинарный файл на этапе сборки и запускает его в небольшом рабочем образе.
Конфигурация выполнения передаётся через переменные окружения в Compose.

### 6. Процессы

HTTP-бэкенд не хранит состояние.
Мониторы и проверки хранятся только в PostgreSQL.
Реестр выполняющихся проверок хранит только временное координационное состояние и не является постоянными бизнес-данными.

### 7. Привязка порта

Приложение самостоятельно запускает HTTP-сервер и слушает порт из `HTTP_PORT`, по умолчанию `8080`.

### 8. Параллелизм

Параллельные проверки выполняются фиксированным пулом рабочих.
Очередь заданий ограничена `JOB_QUEUE_CAPACITY`, поэтому количество задач не растёт бесконтрольно.

### 9. Завершаемость процессов

Приложение быстро создаёт зависимости при старте и обрабатывает `SIGINT`/`SIGTERM`.
Корректное завершение прекращает приём HTTP-запросов, останавливает планировщик, дожидается завершения пула рабочих и закрывает пул PostgreSQL.

### 10. Соответствие сред разработки и эксплуатации

Локальный и контейнерный запуск используют один стек: Go, PostgreSQL, конфигурацию через переменные окружения и SQL-миграции.
SQLite или отдельная база только для разработки не используется.

### 11. Журналы

Логи пишутся только в stdout через `log/slog`.
Логируются запуск приложения, подключение к базе, запуск планировщика и пула рабочих, ошибки проверок и корректное завершение.
Секреты в логах не выводятся.

### 12. Административные процессы

Миграции выполняются отдельной службой Compose с помощью `golang-migrate/migrate`.
Обычный HTTP-процесс не выполняет административные миграции внутри себя.
