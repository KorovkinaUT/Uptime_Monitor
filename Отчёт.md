# Uptime Monitor

## 1. Доменная область

Uptime Monitor предназначен для контроля доступности HTTP/HTTPS-сервисов.
Пользователь создаёт monitor, указывает название сервиса, URL, периодичность проверки, timeout и признак активности.
Приложение автоматически обращается к URL, сохраняет результат в PostgreSQL и показывает текущее состояние и историю проверок.

Проверка считается успешной, если сервис вернул HTTP status от 200 до 399 включительно.
Ответы 4xx и 5xx, timeout, DNS-ошибки и ошибки соединения считаются неуспешными.

## 2. Стек реализации

- Go 1.26
- `net/http` и `chi` для HTTP/REST API
- `pgx/v5/pgxpool` для работы с PostgreSQL
- `log/slog` для структурированных логов
- HTML, CSS и Vanilla JavaScript для frontend
- Docker и Docker Compose
- SQL migrations через отдельный migration service

## 3. Основные сущности

### Monitor

Monitor описывает сервис, который нужно проверять:

- `id`
- `name`
- `url`
- `interval_seconds`
- `timeout_seconds`
- `enabled`

### Check

Check описывает результат одной проверки:

- `id`
- `monitor_id`
- `status` — `up` или `down`
- `status_code`
- `latency_ms`
- `error`
- `checked_at`

Статус `unknown` не является сущностью базы данных. Он вычисляется на уровне API и frontend, если у monitor ещё нет checks.

## 4. Соответствие методологии 12 факторов

### 1. Codebase

Весь проект находится в одном Git-репозитории и представляет собой единую кодовую базу.

### 2. Dependencies

Все Go-зависимости явно объявлены в `go.mod`, а их версии зафиксированы в `go.sum`.  
Окружение приложения воспроизводимо с помощью Docker.

### 3. Config

Все параметры, зависящие от окружения, передаются через переменные окружения: порт HTTP-сервера, строка подключения к PostgreSQL, параметры `worker pool` и `scheduler`.

Пример конфигурации находится в `.env.example`. Локальные значения могут задаваться через `.env`, который не хранится в репозитории.

### 4. Backing services

PostgreSQL рассматривается как внешний подключаемый ресурс. Строка подключения передаётся приложению через `DATABASE_URL`.

Для подключения другого экземпляра PostgreSQL достаточно изменить конфигурацию без изменения кода приложения.

### 5. Build, release, run

Этапы сборки и запуска разделены. Dockerfile сначала собирает Go-бинарник на `build`-этапе, после чего готовый бинарник запускается в отдельном runtime-образе.

Конфигурация приложения не встраивается в образ и передаётся через переменные окружения при запуске.

### 6. Processes

Backend является `stateless`: постоянное состояние приложения не хранится в памяти процесса.

Данные о мониторах и результатах проверок хранятся в PostgreSQL. In-memory реестр выполняющихся проверок используется только для временной координации и не содержит постоянных бизнес-данных.

### 7. Port binding

Приложение самостоятельно поднимает HTTP-сервер и принимает соединения на порту, заданном через `HTTP_PORT`.

Для работы приложения не требуется отдельный внешний application server.

### 8. Concurrency

Параллельное выполнение проверок реализовано с помощью ограниченного `worker pool`.

Количество workers и размер очереди задаются конфигурацией, что позволяет управлять уровнем конкурентности без изменения кода приложения.

### 9. Disposability

Приложение поддерживает корректное завершение по `SIGINT` и `SIGTERM`.

Во время graceful shutdown прекращается приём новых HTTP-запросов и заданий на проверку, останавливается `scheduler`, завершается работа `worker pool`, после чего закрывается пул соединений PostgreSQL.

### 10. Dev/prod parity

В разных окружениях используется одинаковый основной стек: Go, PostgreSQL, SQL-миграции и конфигурация через environment variables.

Для локальной разработки не используется отдельная СУБД или альтернативная реализация хранилища.

### 11. Logs

Приложение пишет структурированные логи через `log/slog` в стандартный поток вывода процесса.

Логи не сохраняются приложением в локальные файлы, а их хранение и обработка могут выполняться внешней системой.

### 12. Admin processes

Миграции базы данных запускаются отдельно от основного HTTP-приложения с помощью `golang-migrate/migrate`. В Docker Compose для этого используется отдельный контейнер, поэтому backend не изменяет схему базы данных при старте.
