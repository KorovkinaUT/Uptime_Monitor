# Uptime Monitor

## 1. Доменная область

Uptime Monitor предназначен для контроля доступности HTTP/HTTPS-сервисов.
Пользователь создаёт monitor, указывает название сервиса, URL, периодичность проверки, timeout и признак активности.
Приложение автоматически обращается к URL, сохраняет результат в PostgreSQL и показывает текущее состояние и историю проверок.

Проверка считается успешной, если сервис вернул HTTP status от 200 до 399 включительно.
Ответы 4xx и 5xx, timeout, DNS-ошибки и ошибки соединения считаются неуспешными.

## 2. Стек реализации

- Go 1.26
- `net/http` и `chi` для HTTP/REST API
- `pgx/v5/pgxpool` для работы с PostgreSQL
- `log/slog` для структурированных логов
- HTML, CSS и Vanilla JavaScript для frontend
- Docker и Docker Compose
- SQL migrations через отдельный migration service

## 3. Архитектура приложения

Приложение разделено на слои:

- `internal/domain` содержит модели, статусы и domain validation rules
- `internal/application` содержит use cases, repository interfaces, scheduler, worker pool и in-flight registry
- `internal/infrastructure` содержит PostgreSQL repositories, http/client, http/server и configuration
- `cmd/app/main.go` собирает зависимости и управляет жизненным циклом приложения

Зависимости направлены от infrastructure к application и от application к domain.
Domain не знает о PostgreSQL, HTTP server, Docker и конкретном драйвере базы данных.

## 4. Основные сущности

### Monitor

Monitor описывает сервис, который нужно проверять:

- `id`
- `name`
- `url`
- `interval_seconds`
- `timeout_seconds`
- `enabled`

### Check

Check описывает результат одной проверки:

- `id`
- `monitor_id`
- `status` — `up` или `down`
- `status_code`
- `latency_ms`
- `error`
- `checked_at`

Статус `unknown` не является сущностью базы данных. Он вычисляется на уровне API и frontend, если у monitor ещё нет checks.

## 5. Структура базы данных

Используются две таблицы: `monitors` и `checks`.

Таблица `checks` ссылается на `monitors` через foreign key `ON DELETE CASCADE`, поэтому hard delete monitor удаляет связанные проверки.
Для выборки истории создан индекс `(monitor_id, checked_at DESC)`.

Current status не хранится в `monitors`.
Последний check выбирается через `LEFT JOIN LATERAL` для списка monitors и через сортировку по `checked_at` для одного monitor.

## 6. REST API

API использует HTTP/1.1 и JSON.

- `POST /api/v1/monitors` — создание monitor
- `GET /api/v1/monitors` — список monitors с последним check без N+1 queries
- `GET /api/v1/monitors/{id}` — получение monitor
- `PUT /api/v1/monitors/{id}` — полное обновление monitor
- `DELETE /api/v1/monitors/{id}` — hard delete
- `GET /api/v1/monitors/{id}/checks?limit=N` — история проверок
- `POST /api/v1/monitors/{id}/check` — ручная проверка

Ошибки возвращаются JSON-объектом с полем `error`.
Некорректный input даёт `400`, отсутствующий monitor — `404`, уже выполняющаяся проверка — `409`.

## 7. Логика мониторинга

HTTP checker создаёт request через `http.NewRequestWithContext` и ограничивает его timeout конкретного monitor.
Response body не читается полностью, но всегда закрывается.
Стандартное поведение Go HTTP client для redirects сохраняется.

Latency измеряется от создания request до получения response или transport-level ошибки.
При отсутствии HTTP response `status_code` равен `NULL`.

Ошибки проверки являются ожидаемым результатом мониторинга и сохраняются как `down`, поэтому ручной check возвращает `200` с результатом проверки.

## 8. Scheduler и worker pool

Scheduler работает централизованно и не создаёт отдельную бесконечную goroutine на каждый monitor.
Он периодически получает из repository только enabled monitors, для которых наступило время проверки.

Перед добавлением job в bounded channel monitor захватывается в in-flight registry.
Worker освобождает его после завершения проверки и сохранения результата.
Та же registry используется ручным endpoint-ом, поэтому duplicate concurrent checks блокируются.

Количество workers и размер очереди задаются environment variables.

## 9. Соответствие методологии 12 факторов

### 1. Codebase

Весь проект находится в одном Git repository и представляет собой один codebase.

### 2. Dependencies

Все Go-зависимости объявлены в `go.mod` и зафиксированы в `go.sum`.
ORM и неявные системные зависимости для работы приложения не используются.

### 3. Config

Environment-specific значения вынесены в environment variables: порт HTTP server, PostgreSQL connection string, параметры worker pool и scheduler.
Пример конфигурации находится в `.env.example`.
Локальные dev-значения находятся в `.env`. Timeout подключения к PostgreSQL и graceful shutdown задаются через environment variables, а timeout Docker healthcheck зафиксирован в Compose.

### 4. Backing services

PostgreSQL подключается как attached backing service через `DATABASE_URL`.
Приложение не зависит от локального файла базы данных.

### 5. Build, release, run

Dockerfile отдельно собирает бинарный файл на builder stage и запускает его в небольшом runtime image.
Runtime configuration передаётся через environment variables в Compose.

### 6. Processes

HTTP backend stateless.
Monitors и checks хранятся только в PostgreSQL.
In-flight registry хранит только временное coordination state и не является persistent business data.

### 7. Port binding

Приложение самостоятельно запускает HTTP server и слушает порт из `HTTP_PORT`, по умолчанию `8080`.

### 8. Concurrency

Параллельные проверки выполняются фиксированным worker pool.
Очередь jobs ограничена `JOB_QUEUE_CAPACITY`, поэтому количество задач не растёт бесконтрольно.

### 9. Disposability

Приложение быстро создаёт зависимости при старте и обрабатывает `SIGINT`/`SIGTERM`.
Graceful shutdown прекращает приём HTTP requests, останавливает scheduler, дожидается worker pool и закрывает PostgreSQL pool.

### 10. Dev/prod parity

Локальный и контейнерный запуск используют один стек: Go, PostgreSQL, environment configuration и SQL migrations.
SQLite или отдельная development-only база не используется.

### 11. Logs

Логи пишутся только в stdout через `log/slog`.
Логируются запуск приложения, подключение к базе, запуск scheduler/worker pool, ошибки checks и graceful shutdown.
Secrets в логах не выводятся.

### 12. Admin processes

Миграции выполняются отдельным Compose service через `golang-migrate/migrate`.
Обычный HTTP process не выполняет административные миграции внутри себя.
